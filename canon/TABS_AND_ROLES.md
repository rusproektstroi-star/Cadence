# Организация вкладок и ролей для работы через VM-парк (шаблон, копируется в другие репозитории)

> **Что это.** Обобщённый, не привязанный к конкретному проекту канон: как разложить работу по
> вкладкам терминала/редактора и ролям сессий, когда часть работы идёт на хосте (управление
> VM-парком), а часть — внутри самих VM (роли агентов).
>
> **Как использовать.** Скопировать секцию «Канон» целиком в `CLAUDE.md` (или эквивалент) целевого
> репозитория, подставив реальные имена вкладок/VM этого проекта. Не пересказывать своими словами
> — расхождение формулировок между репозиториями создаёт проблему: два источника одного решения,
> которые со временем разойдутся.

---

## Канон — вкладки терминала при работе через VM-парк

**Два физических места работы, не путать между собой:**

1. **Хост** — Windows-машина с VMware Workstation. Здесь живёт `vmrun`, `.vmx`-файлы, снапшоты,
   `~/.ssh/config` со всеми ключами, и репозиторий оркестратора (`vmfleet`).
2. **Target** — VM с реальным проектом: git-чекаут, dev-серверы, история работы, `tmux`-сессия
   `agents` с двумя ролевыми панелями. Именно здесь живёт состояние, которое нельзя терять.

**Роли не меняются местами. Никогда.** Технический доступ не даёт права на действие: если роли
что-то доступно, но запрещено ниже — она этим не пользуется.

**[OPS-хост] вкладка** — открыта на репозитории оркестратора (`vmfleet`) **на хосте**. Владеет
`vmrun`, снапшотами, клонированием, инвентарём. **Не открывает и не правит код проектов** ни в
одной из target-VM — это не её работа, даже если у неё технически есть SSH-ключ, которым можно
зайти и посмотреть. Коммитит только в свой собственный репозиторий, никогда — в репозиторий
проекта.

**[E] инженер — панель `agents.0` на target.** Подключение — прямо с хоста в `tmux`-сессию
внутри target-VM (`ssh <id> -t 'tmux attach -t agents'`). Пишет код, коммитит, пушит, управляет
dev-сервером через `devctl`. **Не трогает `vmrun`, не клонирует, не создаёт новые VM** — если
чего-то не хватает на уровне парка (новая VM, апгрейд ресурсов, ротация ключа), это запрос к
[OPS-хост], не самостоятельное действие через случайно доступный SSH до хоста.

**[B] бюро — панель `agents.1` на target, и, возможно, ещё одно место.** Если в вашем процессе
бюро также присутствует где-то ещё (отдельная сессия в редакторе, стратегическое обсуждение с
человеком вне VM) — это законное ВТОРОЕ место той же роли, не отдельная сокращённая версия и не
замена ей: запреты («код не пишет, не коммитит, `vmrun` не трогает») действуют одинаково в обоих
местах. Что первично для конкретного момента решает человек/процесс, не смена роли.

**[A] админ** — человек: направление, приёмка, подтверждение необратимых операций (новый клон,
удаление снапшота, апгрейд ресурсов VM — см. правило ниже).

**Необратимые операции над парком требуют подтверждения [A] до выполнения**, не после: новый
`vmrun clone` (место на диске, новая сущность в инвентаре), удаление снапшота, апгрейд/понижение
`memsize`/`numvcpus` выключенной VM, отзыв ключа, которым сейчас пользуется активная сессия.
[OPS-хост] формулирует, что собирается сделать и почему, и ждёт явного «да», а не действует по
умолчанию из факта, что задача была сформулирована.

**Источник правды — файлы репозитория, не память сессии и не переписка между вкладками.** Если
[OPS-хост] и агенты на target координируются напрямую (сообщение между сессиями на одном хосте —
быстрый путь, человек-посредник не нужен для уточнения/синхронизации) — решение или манифест
существует, только если он записан файлом (в репозитории оркестратора для решений об
инфраструктуре, в репозитории проекта — для решений о коде). Сообщением можно позвать, уточнить
состояние, синхронизироваться; нельзя — принять решение и оставить его только в переписке.

## Более тяжёлая альтернатива — редактор с полным GUI вместо headless CLI

Схема выше описывает headless-профиль (Claude Code в терминале на target, никакого GUI). Если
вашему процессу нужен полноценный редактор (VS Code и т.п.) поверх той же VM-модели — типичный
паттерн: третье, ЛЁГКОЕ физическое место («seat») с редактором и Remote-SSH до target, чтобы не
ставить тяжёлый GUI-стек на каждую проектную VM отдельно (память редактора умножается на число
машин, повторная авторизация на каждой). Cadence в текущем виде такую схему не реализует — здесь
это только зафиксировано как готовое архитектурное решение на случай, если вам понадобится
GUI-редактор поверх той же модели хост/target.
