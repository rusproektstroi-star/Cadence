# Чек-лист развёртывания новой проектной машины

Один проход по каждому пункту при каждом `vmfleet clone`. Список не теоретический: каждый пункт
стоит здесь потому, что однажды был пропущен и это стоило времени. Проходить целиком **до** доклада
пользователю — иначе получается россыпь «а вот это тоже забыл» на каждое следующее сообщение.

## Нулевой пункт: проверить, кому принадлежит аппаратная виртуализация хоста

**Делать один раз на хосте, до всего остального.** Если этот пункт пропустить, гости будут вставать
намертво примерно через час после каждой загрузки, и никакие настройки образа не помогут — мы
потеряли на этом сутки и одиннадцать неверных версий подряд.

```powershell
Get-CimInstance -ClassName Win32_DeviceGuard -Namespace root\Microsoft\Windows\DeviceGuard |
  Select-Object VirtualizationBasedSecurityStatus
Get-Service HvHost
```

Нужно: `VirtualizationBasedSecurityStatus = 0` и `HvHost` в состоянии `Stopped`. Если VBS работает
или `HvHost` запущен — аппаратную виртуализацию держит гипервизор Windows, а VMware вынуждена
работать поверх него, в режиме `ULM`, с эмулируемыми таймерами. Лечение — PowerShell от
администратора:

```
bcdedit /set hypervisorlaunchtype off
```

и перезагрузка хоста. Цена: перестают работать WSL2, Docker Desktop и Windows Sandbox — они и VMware
не делят аппаратную виртуализацию. Откат: `bcdedit /set hypervisorlaunchtype auto`.

Проверка на любой запущенной машине — в её `vmware.log` должно быть `Monitor Mode: CPL0`, а не `ULM`,
и ни одной строки со словом `WHP`. Полный разбор с замерами — `docs/OPERATIONS.md` §7.
## Что действительно требует человека — и что нет

Человек нужен в трёх местах:

1. **Создание deploy-ключа** на GitHub — запись в чужой ресурс, подтверждение уместно;
2. **Интерактивный вход `claude`** в панелях — код вставляется в браузере на хосте;
3. **Запись в системный `hosts`** — права администратора Windows.

**Статический IP человека НЕ требует**, вопреки первому впечатлению. На машинах, выросших из образа,
разрешены без пароля конкретные команды: `netplan apply`, `tee`/`chmod` по путям `/etc/netplan/*`,
а также `systemctl`, `apt-get`, `apt`. Проверять **списком**:

```bash
ssh <id> "sudo -n -l"
```

Не проверять `sudo -n true`: `true` в список не входит, проверка провалится всегда и создаст ложный
вывод «нужен пароль». Разбор — `docs/OPERATIONS.md` §0.

## Сразу при клонировании

- [ ] Deploy-ключ создан **с правом записи сразу** (`read_only=false`): read-only ключ выглядит
      рабочим до первой попытки `git push`, и тогда переоформлять приходится всё заново.
      Этот шаг делает человек — давать ему **готовую ссылку и готовый текст ключа**, а не только
      команду: `https://github.com/<owner>/<repo>/settings/keys` → Add deploy key → обязательно
      галка **Allow write access**. Команда `gh api repos/<owner>/<repo>/keys -X POST -f
      title=... -f key=... -F read_only=false` — альтернатива для тех, кому так удобнее
- [ ] `vmfleet clone <id> -Repo git@github.com:... -DeployKey <путь>` — **SSH-форма URL**. С
      `https://` клонирование падает на «could not read Username»: deploy-ключ настраивает только SSH
- [ ] `git log -1` на госте совпадает с последним коммитом в репозитории
- [ ] Обе панели подняты, обе `claude` (не `bash`)

`clone` берёт **текущее состояние образа, а не снапшот** (`vmrun clone ... full` без `-snapshot`).
Значит образ должен быть выключен и в нужном состоянии; снапшот — точка отката, а не источник клона.

## Проверить наследование от образа — фактом, не предположением

- [ ] `ssh <id> "systemctl is-enabled apt-daily.timer apt-daily-upgrade.timer unattended-upgrades.service"`
      → все `disabled`
- [ ] `ssh <id> "lsmod | grep balloon"` → модуль загружен, **счётчик использования `0`**; в `.vmx`
      машины должны присутствовать `sched.mem.maxmemctl = "0"`, `MemTrimRate = "0"`,
      `sched.mem.pin = "TRUE"`. Если balloon активен, гость рано или поздно встанет намертво без
      единой записи об OOM — разбор в `docs/OPERATIONS.md` §7
- [ ] `memsize` в `.vmx` и в инвентаре совпадают и не ниже 3072
- [ ] `numvcpus` — **больше, чем сессий агентов на машине** (при двух панелях это 4, не 2). На двух
      ядрах машина доходит до отказа быстрее, но от зависаний это не лечит: причина не найдена,
      восемь проверенных версий и текущие приборы — `docs/OPERATIONS.md` §7

## Данные со старой машины (если она заменяется)

- [ ] Проверено, есть ли у старой машины `.git`. Если нет — сверить список файлов с деревом
      репозитория (`git ls-tree -r --name-only HEAD` против `find`), а не полагаться на «там
      наверняка просто код»
- [ ] Всё, что лежит локально и не в git (секреты, `.env`, БД, логи реальных прогонов), перенесено
      через нейтральный каталог `~/incoming`, а не напрямую в рабочее дерево
- [ ] Реальные БД — через `pg_dump`/восстановление, не копированием файлов; счётчики строк сверены
      после восстановления
- [ ] Старая машина погашена после переноса, чтобы две версии не работали одновременно

## Сеть

- [ ] Статический IP применён (`netplan apply`) — сессией самостоятельно, см. выше
- [ ] `network.ip` вписан в инвентарь **после** подтверждения, а не до: иначе `status` показывает
      адрес, которого на машине нет
- [ ] `vmfleet ssh-config` выполнен
- [ ] `vmfleet hosts-file` — требует прав администратора, это отдельный шаг

## Запись в инвентаре — полный набор полей

- [ ] Добавлена **сразу после клонирования**: `clone` её не создаёт
- [ ] `id`, `hostname`, `vmx`, `memsize`, `numvcpus`, обе роли агентов с разными `config_dir`
- [ ] `project` — имя проекта, оно же подпись смонтированного диска
- [ ] `network.ip` / `network.hostname` / `network.ports`
- [ ] `github.repo` в SSH-форме и `github.own_repo` — от него зависит, куда пишется правило
      игнорирования каталога обмена: свой репозиторий → `.gitignore`, чужой → `.git/info/exclude`
- [ ] `host.browser_profile` — подбирается скриптом автоматически
- [ ] `host.mount_letter` — **выбирается руками**, автоматики нет. Пул с конца алфавита:
      `X`, `Y`, `Z`, `W`, `V`, `U`
- [ ] `host.mount_label` (имя проекта) и `host.remote_path` (относительно `$HOME` гостя)
- [ ] `guest.inbox_dir` — каталог обмена файлами, внутри `remote_path`
- [ ] `vmfleet validate` зелёный
- [ ] git identity на госте — машинно-специфичные `user.name`/`user.email`, не личные

## Инструменты

- [ ] Доступ к приватной библиотеке решений, если она используется (`agents-md-install`) — **на
      каждой новой машине**, тем же токеном
- [ ] `vmfleet mount <id>` — проверить, что диск смонтировался и файл, положенный с хоста, виден на
      госте. Эта же команда создаёт каталог обмена и правило игнорирования
- [ ] `.gitignore` проекта реально покрывает секреты и локальные конфиги — сверить `git status
      --short` после переноса, а не предполагать
- [ ] Команда запуска dev-сервера (`.devpanel/services.conf` либо `.devctl.conf`) — настоящая и
      **проверена живым прогоном** (ответ по `curl`), а не просто записана

## Хост

- [ ] Локальный клон репозитория лежит там же, где остальные репозитории пользователя — проверить
      до того, как клонировать заново
- [ ] Ярлык браузера создан в этом клоне, номер профиля свободен и в инвентаре, и физически в
      каталоге профилей Chrome

## В конце — один отчёт

Что сделано и что объективно осталось за человеком (deploy-ключ, вход `claude`, запись в `hosts`).
Не по пункту за сообщение.
