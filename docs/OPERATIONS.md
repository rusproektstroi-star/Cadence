# Cadence — операционный runbook

Как это работает и что делать оператору, по каждой части системы. "Почему так, а не иначе" —
в docs/GOLDEN_IMAGE.md (обоснования решений по сборке образа) и в комментариях самого
`vmfleet.ps1`; здесь — только рабочие команды и их поведение.

## 0. `sudo` на гостях — что доступно без пароля и как это правильно проверять

**Не делать вывод «sudo требует пароль» по `sudo -n true`.** Без пароля разрешены конкретные
команды, а не любые; `true` в список не входит, поэтому такая проверка проваливается всегда — и
создаёт ложное впечатление, что нужен человек. Наступали: сессия отказалась отключать таймеры apt и
поставить пакет, хотя оба действия ей были доступны.

**Правильная проверка — посмотреть сам список:**
```bash
ssh <id> "sudo -n -l"
```

Что образ раздаёт без пароля (см. `docs/GOLDEN_IMAGE.md`): `apt-get`/`apt`, `systemctl`, узкий набор
путей `/etc/netplan/*` плюс `netplan apply`, команды обезличивания клона (`ssh_host_*`, `ssh-keygen
-A`, `hostnamectl`) и `psql` от пользователя `postgres`. Всё остальное — включая правку
`/etc/sudoers.d/` — требует пароля, то есть человека. В этом случае не подбирать и не спрашивать
пароль, а дать оператору готовую строку целиком.

## 1. Профиль `headless` — golden-образ

**Что это.** Гость без графики, две роли на машине — `agents.0` = [E] инженер, `agents.1` = [B]
бюро, всегда обе, всегда в этом порядке (позиция гарантирована порядком создания панелей).
Как собирается сам образ и на основании какого замера ОЗУ выбраны параметры — `docs/GOLDEN_IMAGE.md`.

**`inventory.yaml` — поле `profile: headless`.** Пример записи и структура —
`inventory.yaml.example` в корне репозитория. Скопировать в `inventory.yaml` и отредактировать под
свои машины (этот файл в `.gitignore`, ваши реальные адреса/репозитории туда не коммитятся).

**Поднять агентов на машине:**
```bash
ssh <id> "~/start-agents.sh"          # неинтерактивно, поднимет в фоне, если не поднято
ssh <id> -t 'tmux attach -t agents'   # подключиться
```
Панели адресуются `agents.0`/`agents.1`, каждая — свой `CLAUDE_CONFIG_DIR`
(`~/.config/claude-<id>-engineer`, `~/.config/claude-<id>-bureau`) с ролевым `CLAUDE.md`
(`canon/agent-roles/`). Оба агента представляются сами при первом сообщении — роль + проект
(проект берётся из `CLAUDE.md` в корне рабочего репозитория; на голом эталоне без репозитория —
инженер сам спрашивает, какой клонировать, бюро на тот же вопрос пересылает инженеру).

**Командная строка на машине без ручного `Ctrl+B c`** (для случаев, когда физическая прокидка этой
комбинации не работает через терминал/SSH-клиент): оркестратор сам открывает/закрывает отдельное
окно `tmux` (индекс 1, `shell`) рядом с `agents`, не трогая панели `agents.0`/`agents.1`:
```powershell
.\vmfleet.ps1 shell-open <id>    # создаёт (или просто выбирает, если уже есть) окно shell
.\vmfleet.ps1 shell-close <id>   # закрывает его, возвращает фокус на agents
```
После `shell-open` подключение (`ssh <id> -t 'tmux attach -t agents'`) сразу попадает в окно `shell`.

**Проверка, что подняты обе панели, без входа в сессию:**
```bash
ssh <id> "tmux list-panes -t agents -F '#{pane_index} #{pane_current_command}'"
```
Ожидается две строки, обе `claude`. Если панель одна — `start-agents.sh` устарел (старая условная
версия) или манифест ролей не применён — пересобрать с эталона, не патчить руками на живой машине.

**Кросс-ролевая маршрутизация.** Если пользователь задал не тому агенту вопрос по роли напарника —
агент пересылает его напарнику на той же машине, ждёт ответа, показывает на этом же экране. Не
отказывается молча и не пытается ответить за роль, которая ему не принадлежит.

**Механизм — `tmux send-keys`/`capture-pane`, не `SendMessage`/`ListAgents`.** Панели —
независимые процессы `claude` в разных `CLAUDE_CONFIG_DIR`, не подагенты одной сессии —
внутренние средства межагентного обмена их друг для друга не видят. Присылать сразу, не читая и
не дожидаясь строки ввода напарника — сессия не может надёжно отличить настоящий недописанный
ввод человека от уже отправленного сообщения, которое просто не успело обновиться в
`capture-pane`. Детали и пример команд — в каноне ролей `canon/agent-roles/*.CLAUDE.md`.

## 2. Оркестратор

**Терминал на хосте — Windows Terminal, не голая консоль PowerShell.** Голое окно PS7 (то, что
открывается по умолчанию, если не запускать Windows Terminal явно) не даёт открыть рядом что-то
ещё, пока в нём идёт сессия агента — не годится для реальной работы, где параллельно нужны вкладки
для `ssh`/`devpanel`/`mc` и т.п. (см. `docs/GOLDEN_IMAGE.md`/`OPERATIONS.md` §4a про то же самое
на госте). Windows Terminal — сколько угодно вкладок, каждая независима.

**Сессия-агент, работающая с оркестратором, — в своей отдельной вкладке `pwsh`, не там же, где
остальная работа.** Не запускать оркестраторную сессию в той же вкладке, что используется для
чего-то ещё параллельно — тогда `vmfleet status` (первое действие сессии, см. ниже) и остальной
рабочий поток не путаются друг с другом, и вкладку оркестратора всегда легко узнать по содержимому.

**Запуск — только через `pwsh` (PowerShell 7), не через `powershell.exe`.** Скрипт сам это проверяет
(`#requires -Version 7.0`) и откажется стартовать под 5.1 с понятной ошибкой. В новой вкладке
Windows Terminal по умолчанию может открываться `powershell.exe` (профиль "Windows PowerShell"), не
`pwsh` — проверить профиль по умолчанию (Settings → Startup) или запускать явно через профиль
"PowerShell" (7.x). Что именно ломается под 5.1/легаси-оболочками (кириллица в `?????`, ANSI-коды
как текст) и почему — `docs/decisions/orchestrator.md`.

**Перед первым запуском** — открыть `vmfleet.ps1`, отредактировать блок «КОНФИГ» под свой хост:
SSH-пользователь гостевых машин, путь к диску с `.vmx`, подсеть VMware (см. VMware Virtual Network
Editor). Скрипт откажется работать, пока `$SshUser` остаётся плейсхолдером.

```powershell
cd C:\vmfleet    # или куда вы положили этот репозиторий
.\vmfleet.ps1 validate
.\vmfleet.ps1 status
.\vmfleet.ps1 health [-Only <id>]
.\vmfleet.ps1 up [-Only <id>] [-Group <profile>]
.\vmfleet.ps1 down [-Only <id>]
.\vmfleet.ps1 ssh-config
.\vmfleet.ps1 snapshot <id> -SnapshotName <name>
.\vmfleet.ps1 revert <id> -SnapshotName <name>
```

`up`/`down` без `-Only`/`-Group` действуют на весь парк. `up` отказывает целиком, если запрошено
больше `MAX_CONCURRENT` машин, и перед стартом КАЖДОЙ проверяет свободную ОЗУ хоста — ниже порога
останавливает запуск с понятным сообщением, не продолжает до отказа гостя.

**Первое действие сессии-агента, работающей в директории оркестратора** — выполнить
`vmfleet status` и показать парк (включена/выключена, реальный расход ОЗУ хоста по каждой машине +
свободно на хосте, IP, готовые команды включения/выключения и подключения к агентам), не ждать
вопроса. Симметрично самопредставлению агентов в VM. Колонка ОЗУ читает PID процесса
`vmware-vmx.exe` из lock-файла `<uuid>.vmem.lck\*.lck` рядом с `.vmx` (у
`Win32_Process.CommandLine` для этого процесса пусто без прав администратора — так обходится).

**Клонирование проекта:**
```powershell
.\vmfleet.ps1 clone <новый-id> -Repo <git-url> [-DeployKey <путь>]  # клонирует cli-golden,
                                                      # обезличивает MAC, кладёт манифест ролей,
                                                      # клонирует репозиторий В РАБОЧУЮ ДИРЕКТОРИЮ
                                                      # ДО первого запуска панелей
.\vmfleet.ps1 check-sync <id> -LocalPath <путь>      # сверяет git rev-parse HEAD локалка vs VM
```
Обе команды — расширение сверх голого управления парком, каждая описана прямо в коде.

**`clone` дополнительно кладёт ярлык браузера.** Локальный клон репозитория на хосте по схеме
`Documents\<Name>` (имя — из URL репозитория, без `.git`); в его корень кладётся
`open-in-browser.lnk` — обычный ярлык на `chrome.exe --profile-directory="Profile N"`, без URL
внутри (адреса/вкладки хранятся в самом профиле Chrome). Номер профиля выбирается автоматически —
учитывает и уже занятые в `inventory.yaml` (`host.browser_profile`), и реально существующие
каталоги `Profile N` в самом Chrome. Имя ярлыка добавляется в `.gitignore` репозитория проекта
автоматически (сам ярлык host-специфичный, в git не идёт). Если локального клона по ожидаемому
пути ещё нет — ярлык не создаётся, это отмечается в отчёте, не тихий пропуск.

**Команды одной машины без возни с выделением.** Таблицы `status` удобны для чата, но мышью из них
копировать неудобно: выделение тянется через все столбцы, а блочное выделение (Alt+протяжка) есть
не в каждом терминале — в интегрированном терминале VS Code, например, не работает. Поэтому:

```powershell
.mfleet.ps1 connect <id>                  # по одной команде на строку, без таблицы
.mfleet.ps1 connect <id> -Only agents     # кладёт команду прямо в буфер обмена
```
Ключи `-Only`: `ssh`, `agents`, `devpanel`, `power`, `files`.

**Логи** — `logs\YYYY-MM-DD.log`, каждый вызов `vmrun` и ключевые шаги команд, с меткой времени и
кодом возврата (`vmrun` может вернуть 0 при фактической неудаче — код возврата не единственный
сигнал, состояние проверяется отдельно).

## 3. Сетевой контур

**Подсеть — не общая для всех, своя у каждого хоста.** VMware сам назначает подсеть при настройке
виртуальной сети (Virtual Network Editor) — посмотреть там DHCP-пул и свободный диапазон вне него,
вписать в блок «КОНФИГ» `vmfleet.ps1` (`$StaticIpBase`, `$StaticIpRangeStart/End`).

**Назначение статического IP новой машине** — после `vmfleet clone`, вручную (команда печатается
самим `clone`):
```bash
ssh <id> "sed 's/__STATIC_IP__/<ваш-адрес>/' ~/net-template/01-static.yaml.template | sudo tee /etc/netplan/01-static.yaml && sudo chmod 600 /etc/netplan/01-static.yaml && sudo netplan apply"
```
Дальше вручную вписать `network.ip`/`network.hostname` в `inventory.yaml`, затем:
```powershell
.\vmfleet.ps1 ssh-config    # %USERPROFILE%\.ssh\config
.\vmfleet.ps1 hosts-file    # требует прав администратора, без тихого пропуска
```

**`vmfleet activate <id>`/`deactivate <id>`** — лимит одновременно активных проектов (`$MaxActiveProjects`
в конфиге), проверка статического IP. Подъём dev-сервера и монтирование каталога расширения —
через `devctl` на госте (см. §4 ниже); здесь — только сетевая часть и минимальная заглушка.

## 4. Жизненный цикл dev-сервера

**Агенту запрещено запускать dev-сервер напрямую** (`npm run dev` в панели) — только `devctl`.
Команда запуска — из `~/.devctl.conf` (`PROJECT_START_CMD=`, `PORT=`), задаётся при провижининге
проекта, не зашита в `devctl`.

```bash
ssh <id> "~/bin/devctl start"              # или --port N
ssh <id> "~/bin/devctl status"             # JSON: running/listening/established/holders/idle_seconds
ssh <id> "~/bin/devctl hold <who> --ttl 1800"
ssh <id> "~/bin/devctl release <who>"
ssh <id> "~/bin/devctl stop"
```

Watchdog (`devctl-watchdog.timer`, каждые 30с) гасит сервер сам через grace-период после
исчезновения последнего держателя/соединения — вручную ничего делать не нужно. Журнал —
`~/.local/state/devctl/events.log` на госте + копия в `~/workspace/project/.dev-events.log`.

**Порты в обход `devctl` — не автокилл, только показать оператору.** `vmfleet dev-status`
сравнивает реально слушающие порты (`0.0.0.0`/`[::]`, не loopback-only вроде `systemd-resolved`) с
тем, что знает `devctl` + канонические порты — расхождение показывается в отдельной колонке, не
приводит ни к автоматической остановке, ни к диалогу с агентом (оркестратор не ведёт переговоров
с агентом — только показывает оператору).

**С хоста:**
```powershell
.\vmfleet.ps1 dev-start <id> [-Open]   # -Open открывает http://<hostname>:3000 в браузере хоста
.\vmfleet.ps1 dev-stop <id>
.\vmfleet.ps1 dev-status               # таблица по всему парку
.\vmfleet.ps1 dev-reap                 # аварийно погасить все работающие
```
Лимит — не более двух одновременно работающих dev-серверов по парку; `dev-start` третьего
отклоняется с показом двух работающих и их простоя.

### 4a. `devpanel` + `mc` — ручная панель, отдельный слой от `devctl`

Для проектов с несколькими dev-серверами (фронт/бэк/API) — простая ручная панель, без аренд и
автогашения (не заменяет `devctl`, не трогает его состояние). Каждый инструмент — в своей
отдельной вкладке терминала (`ssh <id>`, обычный интерактивный логин-шелл), не внутри
`tmux`-сессии `agents` и без сплита панелей — SSH не ограничивает число параллельных подключений,
разбивать вкладку на панели не понадобилось.

```bash
ssh <id>              # обычное подключение (или из status, колонка Devpanel)
cd ~/workspace/project && devpanel   # голым именем — симлинк в /usr/local/bin/, работает
                                      # в любом контексте входа
```

**Не форсировать через `ssh <id> -t 'команда'`** — рвёт соединение сразу по выходу из `devpanel`
и не оставляет обычный шелл в той же вкладке для остального (`mc`, `git`). Голое имя `devpanel`
(как и `devctl`/`devctl-watchdog`) работает без полного пути и без завязки на вид входа —
симлинки в `/usr/local/bin/` на образе (см. `docs/GOLDEN_IMAGE.md`).

Внутри — таблица сервисов (имя/адрес `IP:порт`/статус/PID, адрес — одним куском, без пробелов
вокруг `:`, чтобы копировался сразу в адресную строку браузера), команды `s N` (запустить), `k N`
(убить), `r` (обновить), `q` (выход); подсказка «нужны все: s 1, s 2...» — всегда, когда сервисов
больше одного. Конфиг — `.devpanel/services.conf` **в самом репозитории проекта**, не в образе
(формат: `имя;порт;команда_старта;команда_бутстрапа;маркер_готовности`, по строке на сервис) —
`devpanel` ничего не знает о конкретном проекте.

`mc` (Midnight Commander) и `gh` — рядом, для файловой панели/GitHub CLI: `ssh <id>`, затем `mc`
или `gh ...` в отдельной же вкладке (системные пакеты, в `PATH` при любом входе). Полный список
установленного на образе — `~/docs/canon/installed-tools.md` на самом госте; краткая версия того
же списка показывается баннером при обычном логин-входе (`~/.bashrc`, не в панелях `agents`).

## 5. Перенос файлов из `.gitignore` (БД и т.п.) с хоста на VM

**Ситуация.** Файл в `.gitignore` проекта (типично — файл локальной БД) не приходит на VM при
`vmfleet clone`/обычном `git clone` внутри гостя — на госте оказывается пустая/только что
созданная версия, а нужная (с данными) есть только на хосте, в локальном клоне репозитория.
Инженер внутри VM не может дотянуться до хоста напрямую (иначе не был бы нужен git) — перенос
делает оператор/оркестратор с хоста.

**Не класть файл в репозиторий проекта на госте напрямую** (`scp` сразу в
`~/workspace/project/...`) — оркестратор не работает внутри проектных репозиториев гостевых машин.
Вместо этого — нейтральный промежуточный каталог + перекладывание силами инженера (он и так штатно
работает внутри репозитория):

```powershell
# 1. с хоста — файл в нейтральный каталог на госте, НЕ в репозиторий
ssh <id> "mkdir -p ~/incoming"
scp "<локальный путь к файлу>" <id>:~/incoming/<имя_файла>
```

```bash
# 2. сообщить инженеру (agents.0) через tmux send-keys:
ssh <id> "tmux send-keys -t agents:0.0 'текст с путём и целевым файлом'"
ssh <id> "tmux send-keys -t agents:0.0 Enter"
```

Дальше инженер сам делает `mv ~/incoming/<файл> ~/workspace/project/<целевой путь>` и проверяет, что
приложение подхватило новый файл (перезапуск через `devctl`, если процесс уже держал старый файл
открытым).

## 5a. Монтирование рабочего каталога гостя на букву диска хоста

§5 — про разовый перенос файла командой. Монтирование — про регулярный обмен: перетащил файл в
проводнике, агент видит его как обычный локальный файл. Разбор решения — `docs/decisions/mounts.md`.

**Предпосылки (один раз на хост, инсталляторы с UAC — ставит человек):**
[WinFsp](https://github.com/winfsp/winfsp/releases), затем
[SSHFS-Win](https://github.com/winfsp/sshfs-win/releases). Без них команды не падают ошибкой
`net use`, а печатают, чего не хватает.

Ставятся они в **разные** каталоги: WinFsp — 32-битный инсталлятор, кладёт себя в
`Program Files (x86)` и пишет ключ в `WOW6432Node`; SSHFS-Win — в обычный `Program Files`. Проверка
предпосылок это учитывает (оба каталога + реестр), но при ручной сверке смотреть надо оба места.
Если `winget` ругается `0x8a15000f` («Data required by the source is missing» — сломанный кэш
источника), проще взять .msi прямо со страниц релизов, чем чинить winget.

**Поля инвентаря** (пример — `inventory.yaml.example`):
```yaml
    project: my-project
    github:
      own_repo: true                     # true -> screenshots/ в .gitignore; false -> .git/info/exclude
    host:
      mount_letter: "X"
      mount_label: "my-project"          # подпись диска — имя проекта, не id машины
      remote_path: "workspace/project"   # относительно $HOME гостя
    guest:
      inbox_dir: "screenshots"
```

**Команды:**
```powershell
.\vmfleet.ps1 mounts              # таблица: буква, проект, машина, путь, состояние
.\vmfleet.ps1 mount <id>          # смонтировать (машина должна быть включена)
.\vmfleet.ps1 unmount <id>        # снять
```
`activate <id>` монтирует сам, `deactivate <id>` и `down` — размонтируют, причём `down` делает это
**до** выключения машины: выключить ВМ с живым монтированием — оставить зависший дескриптор, который
снимается только перезапуском проводника.

**Передача файла — весь путь:**

1. на хосте перетащить файл в `X:\screenshots` (обычный диск в проводнике; запись уходит по SSH
   сразу на диск гостя, копии на хосте не остаётся);
2. в панели агента сослаться относительным путём от корня проекта: `@screenshots/имя.png` — рабочий
   каталог агента и есть то, что смонтировано, поэтому относительный путь совпадает;
3. «посмотри скриншот» без имени тоже работает: блок, который `mount` дописывает в `CLAUDE.md`
   проекта, велит агенту взять самый свежий файл в каталоге и уточнить, тот ли это.

Буква, состояние и готовая подсказка печатаются в `.mfleet.ps1 status` — колонка **Диск** в первой
таблице и колонка **Файлы** в таблице Connect.

**Как это устроено внутри** (важно при разборе отказов): монтирует не `net use`, а сам оркестратор —
запускает `sshfs-win.exe` в сессии пользователя. Через `net use` работу забирает служба
WinFsp.Launcher, а в её контексте не читается `~/.ssh/config` пользователя, ключ не находится и
монтирование падает с «System error 67». Отсюда же требование: в UNC идёт **алиас** машины из
`~/.ssh/config` (он же `id`), а не `.test`-имя и не IP — `IdentityFile` прописан именно на алиас.
Том держит процесс `sshfs.exe`, поэтому `unmount` останавливает записанный при монтировании PID
(файл `logs/mounts-state.json`); `net use /delete` тут не работает — такого подключения в таблице
сетевых дисков нет.

**Что `mount` делает дополнительно:** создаёт `inbox_dir` на госте, прописывает правило игнорирования
по полю `github.own_repo` и дописывает в `CLAUDE.md` проекта блок про этот каталог
(`canon/project-screenshots-block.md`), если его там ещё нет. Правка **не коммитится** — репозиторий
проектный, коммит за его инженером.

**Разбор ситуаций:**

| Симптом | Причина | Что делать |
|---|---|---|
| Проводник виснет при открытии диска | машина выключена или потеряна сеть | `mounts` покажет состояние, `unmount <id>` снимет |
| Буква занята другим устройством | конфликт с физическим/сетевым диском | ошибка вылезает на `validate`, а не при монтировании — сменить `mount_letter` |
| Файл записался, агент его не видит | путь не от корня проекта | ссылаться `@screenshots/имя.png`, панель запущена с `cd` в каталог проекта |
| Монтирование отвалилось после перезапуска сети | потерян SSH | повторить `mount <id>`, не переподключать вручную в проводнике |
| «Не установлено: WinFsp, SSHFS-Win» | предпосылки не поставлены | поставить оба инсталлятора — это шаг человека, UAC |

## 6. Доступ к приватной библиотеке эталонных решений — точечно, не через golden

**Что это.** Если у вас есть закрытая библиотека готовых решений (сняты с прошлых проектов —
паттерны, готовый код на типовые разделы), которую engineer-роль должна проверять перед тем как
писать типовой код с нуля — доступ к ней даётся точечно, на конкретную проектную VM, никогда через
golden-образ. **Никогда не устанавливается на `cli-golden`** — библиотека и токен не должны попасть
в образ, который может пойти в публичный репозиторий.

**Команда (не часть `clone` — отдельная, применяется к уже существующей или свежесозданной VM):**

```powershell
.\vmfleet.ps1 agents-md-install <id> -Token <путь к файлу с fine-grained PAT> -LibraryRepo <owner/repo>
```

Устанавливает токен в `~/.config/agents-md/token` на госте (`chmod 600`) и логинит `gh` под ним
(`gh auth login --hostname github.com --with-token`) — без единого `git clone`. Дальше engineer-роль
читает библиотеку исключительно через `gh api` (`repos/<owner/repo>/contents/...`,
`--jq '.content' | base64 -d`) — контент никогда не сохраняется на диск как файл, читается прямо в
контекст сессии и адаптируется в новый код проекта.

**Токен — не в этом репозитории, не в образе.** Сам fine-grained PAT (репозиторий только вашей
библиотеки, право только `Contents: Read-only`) хранится вне репозитория, например рядом с
`inventory.yaml` (тот же `.gitignore`) — `vmfleet.ps1` принимает путь к нему параметром `-Token` и
ничего не хранит у себя. Каждый, кто использует этот механизм, заводит свою собственную библиотеку
и свой собственный токен тем же способом — ни то, ни другое не публикуется вместе с оркестратором.

**Если fine-grained PAT возвращает `404 Not Found`** с заголовком
`X-Accepted-Github-Permissions: metadata=read` в ответе GitHub — токен не получил доступ к
репозиторию при создании. Проверить в настройках токена: Repository access → «Only select
repositories» → нужный репозиторий выбран явно; Permissions → Contents: Read-only. Донастройка
прав на уже существующем токене не меняет его значения — переустанавливать на VM не нужно.

## 7. Разобранные отказы — что это было и что делать

Не теория: каждый случай наступал на живом парке.

### Машина включена, Tools живы, но не отвечает ни на SSH, ни на ping

**Картина.** `vmrun list` показывает машину включённой, VMware Tools числятся работающими, гость не
отвечает, журнал гостя обрывается. Перед обрывом в `journalctl` — `workqueue: psi_avgs_work /
blk_mq_run_work_fn / vmballoon_work hogged CPU`, счётчики растут лавиной.

**Причина — не OOM-killer**: до него ядро не дошло, оно встало раньше, на тред-локе по памяти при
активном `vmw_balloon`. Спусковой крючок в нашем случае — ежедневный `apt-daily-upgrade.service`
поверх двух работающих TUI-сессий агентов при ~790 МБ доступной памяти.

**Что сделано на уровне образа** (наследуют все новые клоны):
```bash
sudo -n systemctl disable --now apt-daily.timer apt-daily-upgrade.timer \
                                unattended-upgrades.service fwupd-refresh.timer motd-news.timer
```
**Одних таймеров мало.** `unattended-upgrades` — отдельная служба, планирует себя сама и переживает
отключение таймеров (нашли на живой машине: процесс висел ещё 50 минут после того, как таймеры уже
были сняты). `fwupd-refresh` обновляет прошивки — на виртуалке бессмысленно, `motd-news` тянет
новости по сети ради баннера при логине.

Обновления пакетов — только руками и осознанно. На лабораторном парке в NAT-сети это осмысленный
размен: фоновый apt дороже, чем польза от него. Если ваш парк смотрит наружу — решайте отдельно.

**Если уже случилось.** `soft`-стоп не сработает (гость не принимает команду), `down` сам перейдёт
на `hard`. После подъёма проверить, что поднялись обе панели.

**ПРИЧИНА НАЙДЕНА (2026-09-20): VMware работала не на своём гипервизоре, а поверх виндового —
режим ULM. Лечится одной командой на хосте.** Одиннадцать версий до этого проверены и отпали,
таблица ниже. Сначала лечение, потом измеренный механизм, потом чем опровергнута каждая версия.

### Лечение

В PowerShell **от администратора** на хосте:

```
bcdedit /set hypervisorlaunchtype off
```

Перезагрузить хост. Откат — `bcdedit /set hypervisorlaunchtype auto` и перезагрузка.

Дополнительно, если гипервизор Windows всё равно поднимается (его тянут WSL2, Docker Desktop,
Windows Sandbox, «Целостность памяти» в «Изоляции ядра»):

```
dism /online /disable-feature /featurename:Microsoft-Windows-Subsystem-Linux /norestart
dism /online /disable-feature /featurename:VirtualMachinePlatform /norestart
dism /online /disable-feature /featurename:HypervisorPlatform /norestart
```

`Disable-WindowsOptionalFeature` в PowerShell 7 падает с `Class not registered` — это командлет из
Windows PowerShell 5.1. Через `dism` работает всегда.

**Цена:** WSL2, Docker Desktop и Windows Sandbox перестают работать. Вместе с VMware на одном
процессоре они не уживаются: кто первый занял аппаратную виртуализацию, тот и держит.

### Как проверить, что лечение применилось

В `vmware.log` любой машины:

```
до:     Monitor Mode: ULM      + строки "Syncing WHP TSCs"
после:  Monitor Mode: CPL0     + строк про WHP ноль
```

`ULM` (User Level Monitor) означает, что VMware исполняется поверх гипервизора Windows и таймеры
гостю эмулируются. `CPL0` — собственный монитор VMware, процессор отдан напрямую.

На хосте то же самое видно так: `Get-CimInstance Win32_DeviceGuard` показывает
`VirtualizationBasedSecurityStatus = 0`, служба `HvHost` остановлена, процесса `vmmem` нет.

### Подтверждение: замер после лечения

Два прогона по 110 минут, обе машины в режиме `CPL0`. Раньше на 56-61 минуте обе вставали намертво.

Локальный таймер внутри гостя, прерываний в секунду на ядро:

```
минута  1   100        минута 51    96      <- до лечения здесь было 8200

минута 41    88        минута 95    88
```

Дрейф часов ноль на всём протяжении, давление на процессор ноль, нагрузка 0.02-0.36.

Горение процесса виртуалки с хоста, средние по десятиминутным окнам:

### Что при этом происходило в госте

### Что происходит

Гость уходит в режим, где локальный таймер процессора срабатывает **в разы чаще, чем ядро может
запросить**, и все виртуальные процессоры сгорают в обработчике прерываний. Снаружи это выглядит
как зависание: машина не отвечает ни на SSH, ни на ping, а процесс `vmware-vmx` держит полку ровно
по числу vCPU.

Замер на машине в разгоне, за пять минут до отказа — глобальная разбивка процессорного времени за
3 с (в сотых долях ядра, всего доступно 1200 = 4 ядра × 3 с × 100):

```
пользователь       83
система           115
простой           584
ожидание в-в        0
прерывания          0
МЯГКИЕ ПРЕРЫВАНИЯ 213     <- больше, чем система и пользователь вместе
кража               0
```

И сам счётчик, строка `LOC` в `/proc/interrupts`:

```
свежая загрузка     87-117 прерываний/с на ядро
51-я минута           8200 прерываний/с на ядро
```

При `CONFIG_HZ=1000` и включённом бестиковом режиме планировщик физически не может запросить больше
1000 на ядро, а на простаивающей машине обязан давать заметно меньше. Восемь тысяч — это в восемь
раз выше потолка и в семьдесят-девяносто раз выше собственной базовой линии той же машины.

### Почему это объясняет каждый прежний симптом

| Наблюдение | Объяснение |
|---|---|
| Часы гостя отстают, `drift` растёт заранее | Тики теряются |
| Нагрузка низкая, в процессах пусто | Время прерываний процессам не приписывается вообще — ни в `pidstat`, ни в `load` |
| `steal` ровно ноль | Хост время **отдаёт**; гость сжигает его сам |
| Все vCPU ровно по 100 % | Каждое ядро молотит свой поток прерываний |
| `io` и ошибки страниц нули | Прерывания не трогают ни диск, ни память |
| Поток эмуляции устройств почти пуст | Горят именно vCPU, а не `e1000` и не дисковый контроллер |

### Форма кривой и срок

Кривая одинакова на всех машинах: **ровная полка первые 10-20 минут, затем излом, затем ускоряющийся
рост с удвоением**. Последние полторы минуты перед отказом счётчик удваивается за минуту.

**Чего мы про неё не знаем.** Ключей на ней нет, SSH мы туда не настраивали, поэтому «зависла ли
она» с точки зрения пользователя — не проверено. Измерено только горение снаружи. Возможно, она

**И честно о том, что я оборвал сам:** машину я погасил на 66-й минуте, чтобы вернуть резерву

### Ловушки замера, на которых мы обожглись

- **Делитель интервала.** `watch-fleet.ps1` делил прирост процессорного времени на плановые 15 с,
  тогда как виток растягивался до 25 с: проверка порта 22 у мёртвого гостя висит на таймауте.
  Проценты были завышены в полтора раза, и на них едва не построили вывод. Исправлено 2026-09-20.
- **Порог по потокам.** Наблюдатель считал потоки с порогом 0.5 % и час писал «0.0 %» там, где на
  деле было 14 %: столько, размазанные по восемнадцати потокам, в порог не попадают. Мерить процесс
  целиком.
- **Якорь `^LOC`.** Строка в `/proc/interrupts` начинается с пробелов, шаблон не совпадает никогда и
  молча возвращает пустоту, а та при вычитании превращается в ноль. Сравнивать первое поле целиком.
- **`pgrep -f claude` ловит собственную оболочку**, в командной строке которой есть это слово.
  Рассылка сигнала по такому списку подвешивает саму сессию. Выбирать по имени процесса (`comm`).

**Ловушка, в которую попали обе разбиравшие сессии:** штатные периодические события легко принять за

**Чем ловить следующий раз — два показателя, добавленные в `golden-image/bin/vitals` 2026-09-20.**
Прежний сэмплер честно записал, что все vCPU прижаты, но не мог сказать, где теряется время.
Добавлено, оба читаются без прав root:

- `steal` — доля времени, которую гость просил у гипервизора и не получил;
- `psi[cpu=… mem=… io=…]` — встроенные в ядро счётчики давления (`/proc/pressure`).

Разводят оставшиеся версии однозначно:

| Что покажет замер | Вывод |
|---|---|
| `steal` большой | Хост не отдаёт время — искать в гипервизоре и планировщике хоста |
| `psi mem` большой | Возврат и уплотнение памяти внутри гостя, несмотря на свободные мегабайты |
| `psi io` большой | Дисковый слой, вопреки нулевой очереди снаружи |
| Всё около нуля, vCPU прижаты | Вечный цикл в ядре гостя — снимать стек ядра, нужен root |

В аварийный снимок добавлены полное давление по подсистемам, `wchan` лидеров (функция ядра, в
которой застрял процесс), счётчики уплотнения памяти из `/proc/vmstat` и таблица прерываний.


**(историческая версия, оказалась неполной) Balloon-драйвер.** Машина встала и после увеличения
памяти. В журнале гостя за ту загрузку — **ноль** записей об OOM и нехватке памяти, зато
`vmballoon_work` раз за разом захватывает CPU, а рядом лавиной идут `psi_avgs_work`,
`drain_vmap_area_work`, `vmstat_update`. Гость не упирался в свой потолок: память у него **отбирал
гипервизор**, хотя на хосте было свободно 13–15 ГБ. Это поведение VMware Workstation по умолчанию
(память гостя разрешено подрезать и свопить), и никакой `memsize` от него не спасает.

**Лечение — запретить это в `.vmx` машины и образа (клоны наследуют):**
```
sched.mem.maxmemctl = "0"     # шару не расти: balloon-драйвер память не отбирает
MemTrimRate = "0"             # не подрезать память гостя
sched.mem.pin = "TRUE"        # память гостя держится в физической ОЗУ хоста, не уходит в своп
```
Применяется на выключенной машине. Проверка после старта: `lsmod | grep balloon` — модуль загружен,
но счётчик использования `0`. Условие применимости: на хосте достаточно физической памяти, чтобы
удержать все поднятые гости целиком, — иначе `pin` упрётся в сам хост.

**Про отключение фоновых задач — оно не было лишним, но и не было решением.** Через полтора часа машина встала повторно, уже при отключённых
таймерах и без единого следа apt в журнале: та же лавина `psi_avgs_work` и `vmballoon_work`
(счётчики 35 → 67 → 131). Фоновые задачи были лишь удобным спусковым крючком; причина — теснота.
Настоящее лекарство — память.

### Памяти впритык на проектной машине

`memsize` профиля выбирается под бюджет хоста на момент сборки. Запас полезен, но **зависания
лечились не им**: очередная остановка случилась уже на увеличенной памяти, причина была в
balloon-драйвере (см. выше). Не повторять ошибку «мало памяти — добавим памяти», не посмотрев
сперва, есть ли в журнале гостя хоть одна запись об OOM. Базовое значение поднято до **3072**, в том числе на
самом образе, чтобы новые клоны рождались уже с ним. Замер после увеличения: доступной памяти стало
1810 МБ вместо 717 МБ.

Уже существующей машине память меняется точечно — на выключенной:

1. `.\vmfleet.ps1 down -Only <id>`;
2. в `inventory.yaml` — новое значение `memsize`;
3. в `<VmxRoot>\<id>\<id>.vmx` — строка `memsize = "..."` тем же числом;
4. `.\vmfleet.ps1 validate`, затем `up`.

Поднимать всем подряд не нужно: бюджет хоста общий, и `up` откажет, когда свободной памяти станет
меньше порога. Решение по каждой машине — отдельное, по факту нагрузки.

### Ложный вывод «sudo требует пароль»

См. §0: проверять `sudo -n -l`, а не `sudo -n true`.
