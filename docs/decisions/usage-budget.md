# Бюджет лимитов: посадка сессии на 97 % и подъём после сброса

**Статус:** реализовано и проверено на живой машине парка 2026-09-20.
**Среда:** Claude Code 2.1.269, учётная запись с подпиской (поля `rate_limits` приходят).

Две разные задачи, которые легко перепутать:

| | Что делает | Когда нужна |
|---|---|---|
| **Посадка** | Агент сам следит за расходом и доводит работу до конца **до** обрыва, завершаясь на 97-99 % | Всегда. Делается первой |
| **Подъём** | После сброса лимита работа продолжается с того места, где остановилась | Когда посадка не успела: лимит кончился посреди задачи |

Посадка предотвращает обрыв, подъём его лечит. Поэтому сначала посадка: она дешевле, надёжнее и
делает подъём редким событием, а не нормой.

## Главное: внешний будильник не нужен

Первая мысль была — завести бесплатную модель на стороне (Google AI Studio), которая переживёт
лимит, дождётся сброса и разбудит панель. **Это не нужно.** Claude Code отдаёт всё сам:

- расход по лимитам и время их сброса приходят в скрипт строки состояния (`statusLine`) при каждом
  ответе модели — опрашивать ничего не надо;
- **скрипт строки состояния запускается заново в тот момент, когда окно лимита достигает своего
  `resets_at`** — это и есть готовый сигнал «лимит сброшен», встроенный в инструмент.

Внешняя модель понадобилась бы только чтобы *решать*, что возобновлять. Но это решение дешевле и
надёжнее берётся из файла передачи, который сессия пишет при посадке, — детерминированно, без
второй модели и без ещё одного ключа в секретах.

## Откуда берутся числа

Скрипт строки состояния получает на вход JSON. Значимые поля
([документация](https://code.claude.com/docs/en/statusline)):

```
rate_limits.five_hour.used_percentage     0..100   расход пятичасового окна
rate_limits.five_hour.resets_at                    unix-время сброса
rate_limits.seven_day.used_percentage     0..100   расход недельного окна
rate_limits.seven_day.resets_at
context_window.used_percentage            0..100   заполнение окна контекста
context_window.remaining_percentage
session_id, transcript_path, model.id, cost.total_cost_usd
```

**Ограничения, которые нельзя игнорировать:**

- `rate_limits` появляется **только у подписчиков claude.ai Pro и Max** и **только после первого
  ответа модели** в сессии. На машине с оплатой по API-ключу этих полей не будет вовсе;
- любое окно может отсутствовать по отдельности, и Claude Code убирает окно, когда его `resets_at`
  прошёл. Читать через `// empty`, а не считать отсутствие нулём;
- `context_window.used_percentage` бывает `null` в начале сессии и сразу после `/compact`.

Отсюда правило: **страж работает по тому, что пришло.** Нет `rate_limits` — работает по контексту.
Нет ничего — молчит, а не выдумывает числа.

## Устройство

Две части, обе из документированных механизмов, ничего своего поверх.

### 1. `usage-probe` — скрипт строки состояния

Запускается сам при каждом ответе модели и при сбросе окна лимита. Делает две вещи:

- рисует человеку полосу расхода — то, ради чего строка состояния и существует;
- пишет числа в `~/.local/state/cadence/usage.json` (атомарно, через временный файл и `mv`).

Никакого опроса: событие приходит само. Скрипт обязан быть быстрым — он вызывается часто, Claude
Code гасит частые вызовы окном в 300 мс и **отменяет** незавершённый запуск при следующем событии.
Ничего тяжелее чтения JSON здесь не делать.

**Вторая строка — опознание панели.** Панели всех машин выглядят одинаково, и перепутать их легко,
особенно когда их шесть в разных окнах. Вторая строка приглушена и отвечает на три вопроса:

```
Opus 5 │ 5ч ████████░░ 81% │ 7д 30% │ контекст 43% сброс через 2ч05м
бюро · owner@example.com · my-org/my-project
```

| Что | Откуда | Если нет |
|---|---|---|
| Роль панели | `CLAUDE_CONFIG_DIR`, его задаёт Claude Code процессу панели, скрипт наследует как потомок | опускается |
| Учётная запись | `oauthAccount.emailAddress` из `$CLAUDE_CONFIG_DIR/.claude.json` | опускается (эталон без входа) |
| Репозиторий | `workspace.repo.owner` и `.name` — Claude Code разбирает из `origin` сам | имя рабочего каталога |

Дёргать `git` не нужно: репозиторий приходит во входном JSON уже разобранным. Файл `.claude.json`
весит десятки килобайт, поэтому почта кешируется и перечитывается, только если файл стал новее
кеша — то есть после повторного входа. Строка собирается из непустого: на голом эталоне без входа
и без репозитория она не превращается в частокол разделителей.

### У каждой панели свой файл состояния

Сначала файл был один на машину — и это была ошибка: две панели затирали друг друга. Расход
лимитов у них общий (учётная запись одна), но заполнение контекста своё, и страж читал чужие
числа. Теперь имя файла выводится из `CLAUDE_CONFIG_DIR`:
`usage-claude-<машина>-bureau.json` и `...-engineer.json`. Ролей ровно две, файлы не плодятся.
### 2. `usage-guard` — хук `Stop`

Срабатывает, когда агент закончил ответ, — естественная точка принятия решения. Читает файл
состояния и возвращает `additionalContext`: текст, который видит модель и на который она действует.

Пороги и что говорится агенту:

| Расход | Что получает агент |
|---|---|
| < 80 % | ничего, молчание |
| ≥ 80 % | «Расход N %. Прежде чем брать новую задачу — оцени, влезет ли она целиком» |
| ≥ 92 % | «Расход N %. Новых крупных задач не начинать. Доводить текущую» |
| ≥ 97 % | «Расход N %. Посадка: закоммитить сделанное, записать передачу в HANDOFF.md, закончить» |

Порог берётся по **максимальному** из доступных: пятичасовое окно, недельное и контекст — что
ближе к потолку, то и решает.

Почему `Stop`, а не `UserPromptSubmit`: на машине парка агент работает сам, человек пишет редко.
`Stop` наступает после каждого ответа независимо от того, есть человек или нет.

### 3. `HANDOFF.md` в рабочем каталоге проекта

Что пишется при посадке: на чём остановились, что сделано, что следующее, какие файлы тронуты.
Читается свежей сессией первым делом. Это и есть замена внешней модели: решение «что возобновлять»
принимается тем, кто знал контекст, а не тем, кто пытается его восстановить.

## Подъём после сброса — что останется сделать

Когда посадка заработает, подъём становится простым и **делается на хосте, а не в госте**: сессия,
упёршаяся в лимит, может быть уже завершена, и внутри машины будить некому. Оркестратор жив всегда.

- каждая машина пишет `resets_at` в свой файл состояния (это уже делает `usage-probe`);
- оркестратор читает их и по наступлении времени отправляет в панель `tmux send-keys` — команду
  продолжить по `HANDOFF.md`;
- бот Discord к этому добавляет только уведомление человеку: «лимит на машине X сброшен, работа
  продолжена» — и кнопку «не продолжать», если планы изменились.

## Что уже существует и почему не подходит целиком

- [ccusage](https://github.com/ryoppippi/ccusage) — разбор расхода по локальным журналам, история
  и стоимость. Хорош для отчётов, но это взгляд назад, а не управление сессией;
- [Claude-Code-Usage-Monitor](https://github.com/Maciek-roboblog/Claude-Code-Usage-Monitor) —
  живой терминальный монитор со скоростью сжигания и предсказанием, когда упрёшься. Ближе всего,
  но он показывает человеку, а не говорит агенту;
- встроенные `/usage`, `/status`, `/cost` — интерактивные, из скрипта не читаются.

Ни один не делает того, что нужно: **не сообщает агенту, что пора садиться**. Эту часть придётся
писать самим, и она невелика — два скрипта и файл передачи.

## Установка на машине

Два файла в `~/bin` и блок в настройках **каждого** конфиг-каталога агента — у инженера и у бюро
они разные, и настройки не общие.

```bash
# скрипты
scp golden-image/bin/usage-probe golden-image/bin/usage-guard <id>:bin/
ssh <id> 'chmod +x ~/bin/usage-probe ~/bin/usage-guard'

# подключение в настройки каждого агента, с сохранением того, что там уже есть
ssh <id> 'for d in ~/.config/claude-<id>-bureau ~/.config/claude-<id>-engineer; do
  f="$d/settings.json"
  [ -f "$f" ] || echo "{}" > "$f"
  cp "$f" "$f.bak-before-usage"
  jq --arg probe "$HOME/bin/usage-probe" --arg guard "$HOME/bin/usage-guard" \
     ".statusLine = {type:\"command\", command:\$probe} |
      .hooks.Stop = [ { hooks: [ { type: \"command\", command: \$guard } ] } ]" \
     "$f.bak-before-usage" > "$f"
done'
```

Правка делается через `jq` из копии, а не перезаписью файла целиком: в настройках уже лежат
`model`, `theme`, `env` и прочее, и затирать их нельзя. Claude Code перечитывает настройки сам,
перезапускать сессии не нужно.

**Проверка без ожидания реального расхода** — подать скрипту JSON руками:

```bash
ssh <id> 'printf "{\"model\":{\"display_name\":\"X\"},\"rate_limits\":{\"five_hour\":{\"used_percentage\":81}}}" | ~/bin/usage-probe'
```

Должна появиться полоса и файл `~/.local/state/cadence/usage.json`.

**Откат:** вернуть `settings.json` из `.bak-before-usage` рядом.

## Две ошибки, найденные только на живой машине

Обе тихие — синтаксис верный, скрипт не падает, а данные портятся:

1. **Табуляция как разделитель полей.** `read` схлопывает подряд идущие *пробельные* разделители в
   один, а табуляция пробельная. При отсутствующем поле все последующие значения съезжают влево:
   на машине без `rate_limits` название модели приезжало на место числа. Разделитель заменён на
   `0x1f` — непробельный, пустые поля остаются пустыми.
2. **`printf '--'`** трактует два дефиса как конец опций и падает с `usage: printf`. Печатать
   только через `printf '%s' '--'`.

Обе описаны в комментариях к коду, чтобы не наступили снова.
## Приёмка

1. Строка состояния показывает расход и время сброса на машине парка.
2. Файл состояния обновляется при каждом ответе модели.
3. На 80 %, 92 % и 97 % агент получает соответствующий текст — проверяется подложенным файлом
   состояния с нужными числами, без ожидания реального расхода.
4. На 97 % сессия действительно садится: коммит сделан, `HANDOFF.md` написан.
5. Свежая сессия по `HANDOFF.md` продолжает с того же места.
6. На машине без `rate_limits` (оплата по API-ключу) страж работает по контексту и не падает.
