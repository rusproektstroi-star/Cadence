# Решение: почему оркестратор требует именно `pwsh` (PowerShell 7), не `powershell.exe` 5.1

## Симптом, найденный вживую

При запуске `vmfleet.ps1` из-под легаси-окружения (Windows PowerShell 5.1, `powershell.exe`, или
из-под `cmd.exe`/оболочек с кодовой страницей `chcp 437` по умолчанию) вывод со статусом парка и
логами спотыкался двумя независимыми, легко перепутываемыми друг с другом способами:

1. **Кириллица превращалась в `?????????`.** Русский текст в `Write-Log`/`Write-Host` (сообщения
   статуса, ошибки) читался нормально в самом скрипте, но на экране/в перехваченном выводе шёл
   набор вопросительных знаков вместо букв.
2. **В вывод примешивались ANSI-коды подсветки** (`[32;1m` и подобное) прямо как текст, ломая вид
   markdown-таблиц — это НЕ то же самое, что проблема №1, хотя визуально тоже выглядело как «вывод
   сломан», и легко было спутать причины при первой диагностике.

## Причина — два разных механизма, не один

- **Проблема №1 (кодировка)** — вызывающий процесс (легаси-оболочка) использует кодовую страницу
  437/1251 по умолчанию для консольного вывода, а PowerShell отдаёт строки в UTF-8. Без явного
  согласования кодировки консоли байты кириллицы читаются в чужой кодовой странице и превращаются
  в `?`.
- **Проблема №2 (ANSI)** — это уже поведение самого PowerShell 7: `$PSStyle` по умолчанию
  подсвечивает `Format-Table`/цветной вывод даже когда stdout перенаправлен не в реальный
  терминал, а перехватывается программой (другим процессом, чат-сессией и т.п.) — получатель видит
  сырые escape-последовательности как текст, не как цвет.

## Решение — два независимых фикса, оба нужны одновременно

```powershell
# Фикс №1 — кодировка консоли
try { [Console]::OutputEncoding = [System.Text.Encoding]::UTF8 } catch { }

# Фикс №2 — отключить ANSI-рендеринг, не только для интерактива
$PSStyle.OutputRendering = [System.Management.Automation.OutputRendering]::PlainText
```

Ни один из них не решает проблему другого — были случаи, когда фикс кодировки уже стоял, а
таблицы всё равно ломались ANSI-кодами, и наоборот. Оба фикса — в начале `vmfleet.ps1`,
применяются безусловно, не только при интерактивном запуске.

## Почему `#requires -Version 7.0`, а не просто «рекомендуется pwsh»

Мягкая рекомендация («лучше запускать через pwsh») недостаточна — легко забыть или унаследовать
из окружения, где ярлык/автозапуск указывает на `powershell.exe` 5.1 (частый случай на Windows,
где это исторически путь по умолчанию). `#requires -Version 7.0` — жёсткий отказ с понятной
ошибкой при попытке запустить под 5.1, вместо тихой деградации вывода, которую легко списать на
что-то другое и не связать с версией интерпретатора.

## Практический вывод для тех, кто пользуется этим оркестратором

Открывать `vmfleet.ps1` именно через профиль «PowerShell» (7.x) в Windows Terminal, не через
профиль «Windows PowerShell» (5.1, часто стоит по умолчанию на свежей установке Windows) — см.
`docs/OPERATIONS.md` §2. Если видите `?????????` вместо кириллицы или сырые `[32;1m` в выводе —
это первый признак, что скрипт запущен не под `pwsh`, даже если `#requires` почему-то не сработал
(например, при копировании отдельных строк скрипта в чужую консоль руками, а не запуске файла
целиком).
